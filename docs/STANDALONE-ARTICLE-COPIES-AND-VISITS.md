# Standalone article copies and CMS visits

Administrators can use **複製為草稿** in article management. Articles attached to a newsletter template also offer **從範本建立草稿**. Both open an independent draft in `/admin/article/:articleId/edit`, without attaching it to a newsletter. The existing newsletter composition flow remains available.

`POST /api/cms/articles/:id/duplicate` and `POST /api/cms/articles/:id/from-template` require CMS management permission. Template creation validates an active source and template membership. The transaction preserves content (including YouTube, image and audio markup), author, summary, family targets, taxonomy, media references and active media usage. Placement class restrictions are carried onto the standalone article. IDs, publication state, placement and editorial timestamps are newly owned by the copy. Shared assets are reused; no media object is uploaded or made publicly available. Media inserts tolerate references already generated by R2 database triggers. Any copy failure rolls back the entire operation.

`CmsVisitTracker` records authenticated home and CMS management/editor route visits. It excludes login/logout/callback/error and reader routes, suppresses effect replay and query-only filter changes, and counts returning to a page. POST `/api/cms/visits` records only the signed-in identity, an event UUID, session UUID and validated pathname. Query parameters are omitted. Event UUID conflicts deduplicate retries. Route events have no article/newsletter attribution and cannot inflate their metrics.

The analytics dashboard shows 30-day CMS route visits and unique signed-in users, separately from newsletter reading and email engagement. The aggregate endpoint requires CMS management permission; teachers retain existing scoped article/newsletter analytics. WeeklyReaderPage retains published-content checks and its own article/newsletter attribution. Its view event is claimed before asynchronous logging to avoid StrictMode duplicates, and reading-duration cleanup retains the previous article context.

## Verification

- Focused frontend checks cover article copy actions, standalone editor navigation, route exclusion, filter/revisit deduplication, reader effect replay and analytics routes/dashboard.
- Focused backend checks cover permission boundaries, template validation, class/media/taxonomy copying, failure propagation, visit validation, retry deduplication, transactions and teacher analytics restrictions.
- `npm run build` and `npm run cloudflare:typecheck` validate both runtimes.
- After the backend build, `node scripts/test-standalone-article-copy-db.mjs` checks the real PostgreSQL copy service against R2 triggers, verifies two references/usage counts, and forces a partial failure to verify rollback. It requires a localhost database and rolls back all fixtures/migrations.
- Browser checks verified local Identity sign-in, duplicate creation, standalone editing/saving, template-based standalone creation and the CMS visits card. Two labeled local draft copies and one labeled template were created for these checks.

The delivery journey (login → publish/send → inbox → CMS link → analytics) still requires controlled recipients and separate send authorization. These changes do not deploy, publish or send email.
