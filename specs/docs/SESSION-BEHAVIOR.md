# Persistent CMS identity

Implementation: persistent CMS backend sessions, replacing browser-owned OAuth tokens when `VITE_CMS_SERVER_SESSION=true` and `CMS_SESSION_ENABLED=true`.

Pages forwards `/api/*` through a service binding to the CMS Worker. Login and callback run on that backend using the confidential `email-cms-server` OIDC client, Authorization Code, PKCE, state and nonce. The browser holds a host-only, Secure, HttpOnly, SameSite=Lax opaque cookie. PostgreSQL stores only its SHA-256 identifier hash and AES-GCM encrypted OAuth credentials, bound to that session as authenticated encryption context. No OAuth token is returned by the session API.

CMS identity persists across token expiry, idle time, suspension and reload. The cookie and remembered server record use a rolling 400-day retention window, bounded by browser storage policies; clearing browser data requires sign-in again. This is remembered identity retention, not a 400-day authorization token. Access tokens remain 15 minutes and refresh tokens 30 days. SMZ Identity uses a 30-day central session renewed by verified application use at most once per day. Expired central credentials produce `reauthentication_required`, while confirmed revocation produces `revoked`.

`GET /api/session/current` reports the remembered person separately from authorization status: active, reconnecting, reauthentication_required, revoked or signed_out. Temporary Identity failure preserves identity and the mounted page; no automatic login redirect is issued. The browser retains a non-credential UI snapshot for reload during a backend outage. It never authorizes an API request. Protected operations always require current server verification and current central roles.

The backend coordinates token rotation across Worker instances with a database lease and generation check. It does not hold a database transaction open across Identity requests. Discovery failures release the lease with backoff. Ambiguous token-response failures retry the same request inside Identity's 120-second rotation replay window. If the owner crashes or both exchange responses are lost, the session retains identity but requires reauthentication after the lease expires rather than replaying an old token outside the safe window. Logout and confirmed revocation prevent late refresh results from restoring authority.

Mutations require the exact CMS Origin and `X-CMS-Request: 1`; cookie requests never accept cross-origin writes. The frontend does not replay ambiguous writes. Recovered sessions refresh failed query reads and the dashboard. Article editors preserve per-person, per-document local drafts; a draft from a different document version requires explicit restoration for review. Successful saves clear the draft. Explicit logout and confirmed revocation clear local remembered identity and drafts. An offline logout records a pending marker and retries server revocation before any restoration.

Sign Out revokes the CMS server session and runs the existing central `/logout-all/email-cms-server` coordinator. Central session/grant deletion remains authoritative across linked applications even if a browser prevents front-channel iframe cleanup. Each application independently revalidates before protected operations. Server-cookie cleanup from a third-party iframe can be blocked by browser cookie policies; the CMS browser's pending-logout marker and next same-origin check complete local cleanup.

The technical `email-cms-server` client shares the existing reviewed `email-cms` admission through a fixed server-side mapping. Its own application must also be enabled. No user grants, roles or people are copied or invented. The old public client remains accepted for old open tabs during rollout; a user entering the new server-session flow signs in once to establish the HttpOnly cookie. Old browser credentials are removed after successful server sign-in.

Configuration requires two separate secrets: `CMS_SESSION_SECRET` (32 random bytes, hex encoded) and `CMS_OIDC_CLIENT_SECRET` (confidential client secret shared with Identity registration). CI provisions them, applies the additive `db/migrations/20260913_cms_sessions.sql` migration through the existing CMS Hyperdrive, then deploys Worker and Pages. No new database cluster is provisioned.
